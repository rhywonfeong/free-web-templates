Security & validation baseline

Auth & session handling
Access token (short TTL), refresh token (rotating), HttpOnly cookie, CSRF for forms, device/session listing for admin.
Input validation
Email, phone (E.164), strong passwords, file type/size limits, rate limiting, and sanitization.
Hardening
Helmet, CORS allowlist, secure headers, logging, audit logs, and safe error responses.

User experience requirements

Landing gallery
Paginated event cards, category filters, featured sections, and SEO-friendly pages.
Booking workflow
Step flow: details → review → pay → confirmation → PDF/email. Store drafts and handle payment failures.
PDF confirmation
Generate after payment webhook. Provide download in profile + email attachment/link.

API map (required)

Organized by domain with admin/user separation, webhooks, and uploads.

Auth (User)
  • POST /api/v1/auth/register (name, email, phone, password, avatar)
  • POST /api/v1/auth/login (email, password)
  • POST /api/v1/auth/refresh (refreshToken cookie)
  • POST /api/v1/auth/logout
  • GET /api/v1/auth/me
Auth (Admin)
  • POST /api/v1/admin/auth/register (super-admin only)
  • POST /api/v1/admin/auth/login
  • POST /api/v1/admin/auth/refresh
  • POST /api/v1/admin/auth/logout
  • GET /api/v1/admin/auth/sessions
Events (Public/User)
  • GET /api/v1/events (filters: category, date, price, q, page)
  • GET /api/v1/events/:id
  • GET /api/v1/categories
  • GET /api/v1/events/:id/availability
  • POST /api/v1/events/:id/reviews (auth)
Bookings (User)
  • POST /api/v1/bookings (eventId, date, guests, notes, attachments)
  • GET /api/v1/bookings (mine)
  • GET /api/v1/bookings/:id
  • PATCH /api/v1/bookings/:id (update draft)
  • POST /api/v1/bookings/:id/cancel
Payments (User + Webhooks)
  • POST /api/v1/payments/checkout-session (bookingId)
  • GET /api/v1/payments/status?bookingId=
  • POST /api/v1/payments/webhook (provider signature)
  • POST /api/v1/payments/refund (admin)
Admin (Manage)
  • GET /api/v1/admin/dashboard (KPIs)
  • CRUD /api/v1/admin/events (with cover gallery upload)
  • GET /api/v1/admin/bookings (filters, export)
  • PATCH /api/v1/admin/bookings/:id/status
  • GET /api/v1/admin/users
Important payment rule

Mark booking as paid only from webhook (not from redirect return) to prevent spoofed confirmations. Use idempotency keys to avoid duplicate processing.

Key implementation notes
  • Keep business logic in services; controllers stay thin.
  • Validators per module (Joi/Zod) with a shared validate middleware.
  • Multer upload middleware with file type checks + size limit + antivirus optional.
  • Payment webhooks use raw body parser route only.
  • Generate PDF in background (queue optional) and store URL/path in booking.
Uploads

For Render, prefer S3-compatible storage (or Cloudinary) instead of local disk to avoid ephemeral filesystem issues.

Render deployment checklist

Single Node service hosting SSR pages + APIs, plus DB and storage.

Service setup
  • Build: npm ci
  • Start: node src/server.js
  • Health: GET /health
  • Node version pin via engines
  • Enable auto-deploy from Git
Environment vars
  • DATABASE_URL / MONGODB_URI
  • JWT_ACCESS_SECRET, JWT_REFRESH_SECRET
  • JWT_ACCESS_TTL, JWT_REFRESH_TTL
  • COOKIE_SECRET, CSRF_SECRET
  • PAYMENT keys + WEBHOOK_SECRET
Payment webhooks
  • Set webhook URL: /api/v1/payments/webhook
  • Use raw body parser on webhook route
  • Idempotency on event IDs
  • Verify signature before processing
Production must-haves

Rate limiting on auth routes, strict CORS, secure cookies (sameSite + httpOnly), and disable stack traces in responses.
