The Architecture of Speed

How VijuIT rebuilt the core engine to achieve sub-100ms hydration times, shifting from complex client-side states to a radical island architecture.

Executive Summary

Hypothesis vs Reality

A quick overview of our expectations versus the actual production metrics.

The Hypothesis

VijuIT's platform handles millions of concurrent connections. We hypothesized that moving 80% of component logic to the server would eliminate "spinner fatigue" and reduce client bundle sizes significantly.

The Reality

The transition wasn't just faster; it was transformative for our enterprise clients. First Contentful Paint dropped by 45%, though we had to engineer custom connection pooling to handle the edge-to-database bottleneck.

When we started rebuilding the VijuIT core engine, we knew that traditional SPAs (Single Page Applications) were hitting a ceiling. The "loading spinner" had become a symbol of bloated JavaScript bundles, and our enterprise metrics demanded a change.

01. The Context

In the early days of VijuIT, client-side rendering was the gold standard. We pushed everything to the browser—routing, data fetching, state management. It worked well for small dashboards, but as our enterprise clients scaled to gigabytes of data, the browser main thread started to choke.

We observed Total Blocking Time (TBT) spikes of over 400ms on mid-range devices. This wasn't just a technical metric; it was a UX failure. Users were staring at blank screens while megabytes of JSON were parsed.

"The fastest network request is the one you never make. We realized we were treating the browser as a database, and it was time to stop."

02. The Bottleneck

Our profiling revealed two main culprits: Waterfall requests and Hydration mismatch . Components would mount, fetch data, render children, which would then fetch more data. This sequential chain created a sluggish experience even on fast networks.

03. The Solution

We decided to invert control. Instead of the client asking for data, the server sends the HTML with the data already baked in. We adopted React Server Components (RSC) to keep heavy dependencies on the server.

This wasn't a drop-in replacement. We had to rethink our authentication flow and how we handled real-time updates. We utilized WebSockets for live data, keeping the initial payload purely static HTML.

Solving the Connection Limit

Serverless functions are stateless, meaning every request opens a new database connection. We quickly hit the max connection limit of Postgres. To solve this, we implemented a connection pooler (PgBouncer) and utilized HTTP-based queries for lighter read operations.

// config/database.ts
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20, // Limit active connections
  idleTimeoutMillis: 30000
});

Mutations via Server Actions

Instead of creating API endpoints for every form submission, we moved to React Server Actions. This allowed us to co-locate the mutation logic with the UI component.

The result was a drastic reduction in boilerplate code. No more `useEffect` for data fetching or manual state management for simple CRUD operations.

Strategic Streaming

We wrapped critical UI parts in Suspense boundaries. The navigation and shell load instantly (static), while the heavy data grids stream in parallel.

This creates the perception of instant loading. The user can interact with the menu while the dashboard data is still being fetched from the database.

System Design

Under the Hood

We bypass the traditional API layer. By importing backend logic directly into React components, we eliminate network waterfalls and serialization overhead.

This reduces the Time to Interactive (TTI) by serving non-interactive HTML immediately while hydrating interactive islands (buttons, forms) in the background. 

async function Dashboard() {
  // Direct DB access in component
  const data = await db.query(
    'SELECT * FROM analytics LIMIT 100'
  );

  return (
    <Suspense fallback={<Skeleton />}>
      <Chart data={data} />
    </Suspense>
  );
}

We utilize a `stale-while-revalidate` strategy deployed to global edge nodes. Static content is cached at the edge, while dynamic data is fetched asynchronously.

  • TTL (Time to Live): 60 seconds for dashboard data.
  • SWR: Serves stale data instantly, updates in background.
  • Geo-routing: Requests hit the nearest Vercel Edge region.

The Verdict

Complexity is the price of performance.

Moving to this new architecture wasn't easy. It required a mental shift from "client-first" to "server-first." However, for our enterprise clients where milliseconds translate to revenue, this complexity is an investment that pays dividends.
